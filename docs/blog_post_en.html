1. Introduction: The Untraveled Path — Why Dual 5070 Ti?

In 2026, Qwen 3.8-27B (and the broader Qwen 3.5 family) has established itself as the gold standard of open-weight LLMs. Featuring deep mathematical reasoning, exceptional multilingual fidelity, and a native Vision Transformer (ViT) for multimodal image comprehension, it rivals proprietary frontier models.

However, serving a 27B parameter model with extended context windows (up to 32k tokens) commands a steep minimum of 28GB+ VRAM.

The industry default solution is acquiring a single NVIDIA GeForce RTX 5090 (32GB). Yet that choice comes with severe compromises:

  • Exorbitant Price Tag: A single card commands between $2,500 and $3,200 due to enterprise-tier demand and retail scalping.
  • 575W Single-Die Heat Dissipation: Concentrating 575 watts into one PCIe slot pushes standard chassis airflow and power supplies to their limits.

This spurred a radical engineering thesis: "Can we combine two NVIDIA GeForce RTX 5070 Ti cards (16GB GDDR7, 250W TDP each) to create a 32GB VRAM inference system for ~$1,200 total?" Together, two 5070 Ti cards offer a theoretical aggregate memory bandwidth of 1,792 GB/s and distributed thermal management.

Yet, across Reddit, GitHub, and HuggingFace, virtually no documented case studies existed for running 27B models on Dual 5070 Ti in production. Consumer GeForce cards have had physical NVLink fingers excised, and prevailing wisdom warned that PCIe All-Reduce latency would reduce multi-GPU throughput to an unusable crawl.

We chose to test that conventional wisdom firsthand. This is the chronological, technical record of that journey.

2. Engineering Chronicle: The Six Phases of Trial & Triumph

Phase 1: August 29 – 30
The First Wall: AWQ INT4 & The 16GB VRAM Allocation Crisis

Our initial implementation targeted cyankiwi/Qwen3.8-27B-AWQ-INT4 using vLLM in Tensor Parallelism (TP=2).

The Struggle: CUDA Graph Memory Collisions & Instant OOM

The mathematical assumption was straightforward: a ~15GB quantized model split across two 16GB cards leaves 8.5GB of headroom on each card. Yet upon launching vLLM, the container immediately crashed: 

RuntimeError: Engine core initialization failed.
ValueError: No available memory for the cache blocks.

"Why does a model that boots smoothly on a 32GB single 5090 die with out-of-memory errors on a 32GB dual 5070 Ti setup?"

Root Cause Analysis: In multi-GPU TP=2, each GPU worker allocates its own independent PyTorch context, communication bounce buffers, and critically, dedicated CUDA Graph capture memory (~1.5GB to 2.0GB per GPU). On a 16GB card, model weights plus CUDA Graph allocations left under 300MB for the actual KV cache pool.

Community forums suggested disabling CUDA Graphs via --enforce-eager. However, doing so throttled decode performance below 30 tok/s. We established an uncompromising ground rule: CUDA Graphs must remain active at all costs.

Phase 2: August 31
The PCIe Nightmare & The Collapse of the First PP=2 Attempt

After painstakingly tuning memory parameters to coax the AWQ model into booting under TP=2, initial benchmark numbers proved disheartening:

  • Single Stream Decode: 23.3 tok/s (far too sluggish for interactive chat)
  • Batch Throughput: Rigidly capped at 116 tok/s
  • GPU Power Draw: Stagnant at 188W out of the 250W TDP limit
The Physical Bottleneck: 128 PCIe Round Trips Per Token

Qwen 27B features 64 transformer layers. In TP=2, every forward pass across every single layer requires an All-Reduce exchange across the PCIe bus. Generating a single token necessitated 128 inter-GPU PCIe sync operations. The Tensor Cores spent more time idling for PCIe packets than executing matrix math.

To eliminate inter-layer All-Reduce traffic, we pivoted to Pipeline Parallelism (PP=2). If GPU 0 processes layers 0~31 and GPU 1 handles layers 32~63, inter-GPU communication drops to exactly one exchange per forward pass. However, attempting PP=2 with the AWQ model failed catastrophically at boot: ValueError: No available memory for the cache blocks. In vLLM V1, PP=2 forced the entire embedding layer onto GPU 0 and the full LM Head onto GPU 1, destroying memory symmetry.

Phase 3: September 5
The Turning Point: Blackwell Native NVFP4 & The First PP=2 Boot

The breakthrough arrived with NVIDIA's native Blackwell quantization format: gittensor-model-hub/Qwen3.8-27B-NVFP4-RTX5090.

ModelOpt NVFP4 compressed the model footprint further while aligning natively with Blackwell Tensor Cores. By enforcing explicit KV cache byte bounds (--kv-cache-memory 3031959552) and FP8 KV caching, vLLM booted in PP=2 mode for the very first time:

Single-stream speed registered at 47.7 tok/s. While double the speed of AWQ, it still lagged behind a single 5090 (~75 tok/s).

Phase 4: September 5 – 6
The Siren Song of PP=2 (480 tok/s) and The Multimodal OOM Catastrophe

Under pure offline text workloads, PP=2 unleashed astonishing performance. When the queue was saturated with 14~16 concurrent requests, vLLM's internal logger recorded: 

Engine 000: Avg prompt throughput: 712.2 tokens/s, Avg generation throughput: 480.6 tokens/s (Running: 14 reqs)
Engine 000: Avg prompt throughput: 1154.7 tokens/s, Avg generation throughput: 404.7 tokens/s (Running: 16 reqs)

Peak continuous generation hit 480.6 tok/s! With PCIe All-Reduce overhead eliminated, batch throughput soared 30% beyond our earlier TP=2 attempts. We were convinced PP=2 was the ultimate answer.

The Catastrophe: Vision Enters, System Collapses

The illusion shattered when multimodal image queries entered the workload alongside text. Within seconds, the inference engine crashed: 

(Worker_PP0 pid=213) RuntimeError: Encoder cache miss for 71bbed5ce3add2...
(Worker_PP0 pid=213) ERROR: multiproc_executor.py:1047
vllm-qwen3.8-27b-NVFP4-RTX5090 exited with code 1

"Both cards were idling around 12.5GB. After processing just 3 images, GPU 0 spiked to 15.38GB, froze, and triggered a fatal memory crash!"

The Architectural Flaw: Pipeline Parallelism divides transformer layers sequentially, but the entire Vision Transformer (ViT) encoder was pinned 100% onto GPU 0. Concurrently handling text and high-resolution images overwhelmed GPU 0's 16GB ceiling. Compounded by Qwen 3.8 Mamba state-block collisions (max_num_seqs 256 exceeds available Mamba cache blocks 118), PP=2 proved fatally brittle for hybrid production workloads.

Phase 5: September 25
The Hacked Driver Investigation & The Hardware Rediscovery

With PP=2 disqualified for multimodal stability, we were forced back to TP=2. But how could we eliminate the 128-round All-Reduce bottleneck?

We investigated the open-source community's forbidden territory: Hacked NVIDIA Drivers (aikitoria / tinygrad open-gpu-kernel-modules P2P bypasses):

  • Consumer GeForce silicon possesses hardware P2P DMA capabilities, but NVIDIA driver locks artificially restrict it (CNS: Chipset Not Supported).
  • Community patches inject pKernelBif->p2pOverride = 0x11 to force BAR1 P2P DMA on desktop motherboards.
The Hardware Revelation: ASUS ProArt X870E's Hidden Power

Before risking unverified kernel patches, we conducted an exhaustive hardware audit of our host (gpu2): 

pcie.link.gen.max: 5 (PCIe 5.0 32GT/s Verified)
pcie.link.width.current: 8 (True x8 Symmetric Bifurcation Active)
BAR1 Memory: 16,384 MiB (Full 16GB Resizable BAR Aperture Mapped)

Our motherboard—the ASUS ProArt X870E-CREATOR—was routing CPU-direct lanes symmetrically at PCIe 5.0 x8 / x8. At 31.5 GB/s unidirectional bandwidth, it matches a full PCIe 4.0 x16 slot. We realized we did not need experimental kernel patches: the bottleneck could be broken purely through vLLM communication stack optimization.

Phase 6: September 25 – 26
The Masterpiece: TP=2 Fully Optimized & The 81.3 tok/s Record

We orchestrated four synchronized optimizations across the stack:

  1. --max-num-batched-tokens 8192: Doubled the prefill token limit so 4,105-token inputs execute in a single forward pass without chunking (shaving wall time from 12.7s to 10.6s).
  2. NCCL_BUFFSIZE: "8388608": Expanded the PCIe ring buffer to 8MB, preventing All-Reduce flush stalls across 64 layers.
  3. VLLM_ATTENTION_BACKEND: "FLASHINFER": Bypassed Triton to unleash native Blackwell Tensor Core FP4/FP8 mixed-precision paging kernels.
  4. PYTORCH_CUDA_ALLOC_CONF: "expandable_segments:False": Eliminated memory allocator deadlocks with CUDA Graph capture.

Executing python vllm_bench.py --concurrency 16 revealed unprecedented figures.

4. The Architectural Verdict: TP=2 vs PP=2

The pivotal question remains: "If PP=2 achieved 480 tok/s batch throughput, why is TP=2 the definitive production choice?"

Dimension TP=2 (Final Production Configuration) PP=2 (Pipeline Parallelism) Verdict & Rationale
Single Stream Interactive Speed 81.3 tok/s (Flawless real-time typing) 47.7 tok/s (Noticeable typing lag) TP=2 is +70.4% faster. Decisive for UX
Offline High-Batch Throughput 320 ~ 335 tok/s (Peak 446.5 tok/s) 480.6 tok/s (Maximum throughput) PP=2 wins in batch, but at the cost of halving interactive speed
VRAM Memory Balance Perfect 50:50 distribution (7.8GB : 7.8GB) Severe imbalance (15.4GB vs 13.0GB) TP=2 protects both cards; PP=2 risks single-card blowout
Multimodal (Vision) Resilience Rock solid; ViT split 50:50 Fatal OOM crashes; ViT pinned to GPU 0 PP=2 is completely disqualified for image workloads
Prefix Caching Efficiency Synchronous shared cache blocks Fragmented stage caches Long multi-turn context reuse favors TP=2
The Asymmetry of User Perception

When an end user interacts with a chat application, the difference between 47 tok/s and 81 tok/s is the difference between sluggish waiting and instantaneous response. Conversely, in background batch jobs, whether 50,000 documents take 2 hours or 2 hours and 30 minutes is virtually negligible.

"Sacrificing interactive speed for marginal batch gains is an anti-pattern. Optimized TP=2 provides the holy grail: blazing 81.3 tok/s interactive responsiveness combined with resilient 335+ tok/s batch throughput."

    runtime: nvidia
    restart: always
    ipc: host

      HF_TOKEN: "your_huggingface_token_here"

    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]

      interval: 30s
      timeout: 10s
      retries: 300
      start_period: 600s

    command: >
      --model gittensor-model-hub/Qwen3.8-27B-NVFP4-RTX5090

      --pipeline-parallel-size 1
